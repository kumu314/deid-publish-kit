# deid-publish-kit — 把「只追加留痕」写成能公开的证据

四个小脚本，零依赖（Node 18+，只用标准库）。它们做的是一件很窄的事：
**从一份带完整留痕的母稿，派生出能发到各个平台的稿子，并且在出稿前用机械手段证明它干净。**

它不解决「记忆该怎么设计」——那是写侧的协议与参考实现，另一个立项。
这里只管读侧与发布侧：一条结论怎么带着可复算的证据走出去，且不把内部信息一起带出去。

---

## 为什么要这套东西

四条纪律，每条都是踩出来的。每条下面配一个**编造的**例子，形态与真实事故同构。

### 1. 留痕只追加，所以「推翻」是可以算出来的

只追加的日志不会骗你：先写的那条还在那儿，推翻它的那条也在。两者相减就是间隔。
于是「旧结论被当成现状用了很久」这种指控，可以写成 `11.21d`，而不是形容词。

```text
可写：第一现场 1.04d 之后被更正；更正 5.63d 之后判据才进共享约定
不可写：这两条的行号、写入时刻、写它的人
```

难点不在算，在于**算的过程不能出现在正文里**：一旦正文写了「第 240 行到第 512 行」，
读者里知道内情的人拿行号一查就回到原始时刻。所以差值由脚本产出后粘贴，见 `verify-durations.js`。

### 2. 数字必须是重算出来的，不是回忆出来的

改稿的时候没人会重新核对上一次算过的数。人是会在截止时间前把 `63.17d` 写成 `63.16d` 的，
而这个错**肉眼看不出来**——它就是四舍五入级别的差异。所以每个发布数字配一条可重跑的计算，
并且配一个负对照：`fixtures/rows-bad.json` 与正确样例只差一位，闸门必须为它亮红。

同理，聚合数字要有一个**单一时点的快照**。同一份稿子里「71 天」「6 次推翻」如果来自两次查询，
它们就不是同一件事的描述，而是两件不同事情的描述。

### 3. 认状态字段，不认「看起来像证据」的字段

形态示例：某个确认接口被调用过，就被统计成「对方读过了」，于是得出「协议没人看」的结论。
真相可能是相反的——对方读了、回了、还提了可执行建议，只是从没调用过那个确认接口。

规则：**判断只认能直接观测的字段**；「已读」不是状态字段能定义的东西。
任何用「已读时间戳」「确认调用台账」这类字段推出的「送达率 / 阅读率」结论都要先否证一次：
找出一个「没调用过确认接口、但显然读过」的反例。找到一个，这条判据就作废。

### 4. 机制写下来之后，它自己会变旧

一条判据被写进共享约定，过了十几天，另一个人把已经被推翻的旧说法当事实重新用了一次；
风险卡关掉之后的第一个小时，同一个错又说了一次。

所以这份工具链里没有「写完就信」这一环：
每个环节都要**回读**——派生稿回读成是否逐字等于母稿切片，渲染回读页面内量出的越界标记，
落库回读查库而不是看返回值。返回值说成功不代表库里真有；这条在 `verify-derivation.js`、
`fit.js` 与 README 末段的发布顺序里都是同一条纪律。

## 30 秒上手

```bash
git clone <本仓库地址> && cd deid-publish-kit

# 1) 造你自己的词表（身份名 / 机器名 / 工程名，一行一个）
cp wordlist.example.txt wordlist.txt
cp dates.example.txt dates.txt

# 2) 闸门：先证明它会红，再信它的绿
node leakcheck.js fixtures/sample-dirty.md --wordlist wordlist.example.txt --dates dates.example.txt
node leakcheck.js fixtures/sample-clean.md --wordlist wordlist.example.txt --dates dates.example.txt

# 3) 数字复算（这里用编造的行数据）
node verify-durations.js --fixture fixtures/rows.json
node verify-durations.js --fixture fixtures/rows-bad.json   # 负对照，必须退出 1

# 4) 全流程自检
node selfcheck.js
```

词表文件被 `.gitignore` 挡住了：规则可以公开，名单不行。
**一份公开的词表就是本次脱敏攻击的靶子**——它会告诉读者哪些名字值得反查。

## 脚本清单

| 文件 | 干什么 | 什么时候必须跑 |
| --- | --- | --- |
| `leakcheck.js` | 形态闸门：身份词、日期窗口、时刻、行号、短哈希、路径、邮箱、uuid、凭据形态、裸 IP | 每次改完对外文本 |
| `measure.js` | 码点字数 / 行数 / 字节数，并把稿子里残留的 ISO 时刻列成「距链首第 N 天」 | 每份稿子、每次改完 |
| `derive.js` | 母稿 → 各平台变体（纯 md 版 + 可直接粘贴的 HTML 版），正文切片逐字复制 | 母稿任何一次改动后 |
| `verify-derivation.js` | 证明变体没被手改过（尾段逐字等值 + 40 字滑窗包含；检的是剥离版式后的正文），并抓未解析的 markdown 残留 | 派生之后 |
| `verify-durations.js` | 从原始行时间重算每个相对时长与「第 N 天」，与稿中字符串逐字比对 | 发布前，以及每次改时长 |
| `html2text.js` | 从 HTML 抽读者可见文本，让闸门判内容而不是判标签 | 对 HTML 产物过闸之前 |
| `render.js` + `fit.js` + `cover-guard.js` | 真实 Chrome 无头出图，并把页面内量出的越界标记读回来 | 出图之后，写文案之前 |
| `selfcheck.js` | 上面所有东西的负对照总检 | 提交前 |

## 闸门的三类已知误报（别把它们当成「稿子有问题」）

1. **`https://` 的尾巴像盘符。** `[A-Za-z]:[\\/]` 会命中 `...s:/`，于是一篇带链接的稿子永远红。
   加 `--allow-link`：只把 URL 这一段从盘符规则里抹掉，其它规则仍看原文，
   所以链接里藏着的身份名照样红。输出里 `path_rule_masked_in_urls` 记录被抹掉了几处——
   可解释、可核对，不是一条被静默放宽的规则。
2. **CSS 颜色像短哈希。** `#f6f6f6` 会被 `#[0-9a-f]{3,}` 命中。解法不是关掉规则，
   而是先 `html2text.js` 再 `leakcheck.js`：判内容，不判样式。
3. **短名字乱咬。** 词表里放一个两三个字母的身份名，它会命中大量普通词。
   默认口径是子串命中（宁可多咬，路径里的名字也要抓到）；噪音太吵时对该词表加 `--word-boundary`。

反过来还有两类**闸门看不见**的东西，必须靠人：
- **编码不诚实。** 条高用百分比时，同列里的标签行会把条挤扁，`80` 与 `37` 画出来几乎一样高。
  几何回读只能告诉你「没越界」，它看不出比例撒谎。所以条高用像素，并在图注里写清换算。
- **口径漂移。** 同一句话里「码点数」「字节数」「Word 字数」会差出几十；平台限的到底是哪个，
  见下节，逐项核实过才敢写。

## 平台字数上限（发布口径，按核实程度标注）

| 平台 | 口径 | 状态 |
| --- | --- | --- |
| 公众号 | 标题 64 字符：中文计 1、英数计 0.5；摘要 120 字符 | 已核到官方说明 |
| 公众号 | 已群发后只能改一次，单次改动 ≤ 20 个中文字符 | 已核到官方说明 |
| 小红书 | 标题 20 字、正文 1000 字 | 有官方页；另有帖子称 5000，取小的走 |
| 知乎 | 问题标题约 50 字 | **未核实**，发布前自己数一遍 |

`measure.js` 报的是**码点**数。中文按 1、emoji 按 1，与「英数计 0.5」的平台口径不同，
所以混排稿要按平台规则再折一次。

## 发布顺序（顺序本身是防呆的一部分）

```bash
node derive.js --config derive.json
node verify-derivation.js --master <母稿> --from-section "<切片标记>" \
     --zhihu <纯md版> --wechat <粘贴版html>
node html2text.js <粘贴版html>
node measure.js <各稿>
node leakcheck.js <各稿> <粘贴版的 .VISIBLE-TEXT.txt> --wordlist wordlist.txt --dates dates.txt --allow-link
node verify-durations.js --fixture exports/rows.json
node render.js --spec fit.json && node fit.js --spec fit.json
```

最后一步之后**还要人眼看一遍图**：`fit.js` 只保证不越界，不保证图里的编码说的是真话。

## 本仓库自己的过闸读数

发布这份工具之前，先用**一份真实词表**（不公开，含几十个身份名与一个日期窗口）把仓库里 27 个文件全跑了一遍：

| 规则 | 命中 | 判定 |
| --- | --- | --- |
| 身份名 `name:*` | **0** | 通过 |
| 日期窗口 `date:*` | **0** | 通过 |
| `hashtoken` | 5 | CSS 颜色字面量（`#f6f6f6` 等）与 README 举例引用，非读者可见正文 |
| `path` | 5 | 工具自身源码里的规则字面量（`file:\/+`、被引号包住的 `s:/`）、示例 Chrome 安装路径、`selfcheck.js` 故意植入的坏字符串 |
| 其余 6 类 | 各 1 | 全部落在 `fixtures/sample-dirty.md`——那是设计上必须红的负对照 |

两个口径值得说明，因为它们就是这套工具最容易自欺的地方：

- 这一遍加了 `--word-boundary`。真实词表里有一个两字母身份名，子串口径下它会命中
  `permit`、`pipeline`、`PingFang` 这类普通词（10 处）。**这类命中是词表口径的代价，不是稿件的问题**；
  但反过来，去掉边界之后必须先确认这 10 处确实全是子串误伤，才允许按误伤记账。
- 这一遍也加了 `--allow-link`，它只抹 URL 里的盘符形态；`file://` 只抹前缀，
  尾巴上的本地路径仍然要红——那是这条规则存在的理由。

## 边界

- 本仓库是**发布侧工具链**：脱敏闸门、派生、数字复算、渲染回读。
- 不做记忆协议、不做写侧参考实现、不碰任何具体存储引擎；那是另一个立项，撞车没有意义。
- 不含任何具体系统的词表与数据。所有例子来自 `fixtures/`，里面的人名、日期、行号都是编的。
- 若你把本仓库转成公开项目，请把「谁的名字在哪份名单里」这件事留在私有文件里——
  这条就是 `.gitignore` 存在的全部理由。
